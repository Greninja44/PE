# Fine-tuning: LoRA on Stable Diffusion 1.5 (DiffusionDB)

## Question

Can a lightweight adapter make the **generator** (SD 1.5) reproduce the image a prompt was written for more
faithfully? This complements the main study, which varies the **prompt** (caption vs detailed vs structured vs
refined) while keeping the generator fixed.

## Data

* **Source:** [DiffusionDB 2M](https://huggingface.co/datasets/poloclub/diffusiondb) (Wang et al., 2022), CC0-1.0:
  images generated by Stable Diffusion 1.x from prompts written by Discord users, with prompts and settings.
* **Subset:** parts 1–3 (3,000 images) → `scripts/download_diffusiondb.py --parts 1 2 3`.
* **Filters** (`python -m app.finetune.dataset build`): native 512×512 only (SD 1.5 resolution; no resizing),
  DiffusionDB `image_nsfw` < 0.2 and `prompt_nsfw` < 0.2, non-empty prompt, exact-duplicate images removed.
  Result: **1,109 images kept** (1,598 not 512×512, 247 image-NSFW, 46 prompt-NSFW dropped).
* **Split:** grouped by **normalised prompt text** (SHA-256 bucket, 80/10/10): **898 train / 99 val / 112 test**,
  with **zero prompt groups shared between splits**. Per-image splitting would leak: DiffusionDB has many images per
  prompt and many near-identical prompts. The split is deterministic and independent of which parts are downloaded.
* All data stays in `backend/data/finetune/` (git-ignored); a dataset card with filter counts and manifest hashes is
  written next to the manifests.

## Method

* LoRA (PEFT) on the UNet attention projections `to_q, to_k, to_v, to_out.0`; text encoder and VAE frozen.
* Objective: standard ε-prediction MSE with SD 1.5's DDPM schedule (1000 steps).
* Memory plan for 16 GB: VAE latents (fp32 encode, latent mean × scaling factor) and CLIP text embeddings are
  computed once and cached in fp16; VAE and text encoder are then unloaded. Only the bf16 UNet (frozen) + fp32 LoRA
  weights are trained, with gradient checkpointing, batch 1 and gradient accumulation 4.
* Validation loss on the val split uses **fixed noise and timesteps**, so successive values are comparable. The test
  split is not used in training or checkpoint choice; the **final** adapter is published (no post-hoc selection).
* Every run directory records config, dataset card, code fingerprint, per-step training log, validation log,
  checkpoints, status and peak memory.

```bash
cd backend
.venv/bin/python -m app.finetune.train --name my-run --steps 500 --rank 8 --lr 1e-4
.venv/bin/python -m app.finetune.evaluate --run my-run --n 40
```

Training and evaluation keep the Mac awake (`caffeinate -i`, released afterwards). Without it, the development Mac's
1-minute idle sleep stalled training steps for 200–900 s.

## Evaluation

For the first *n* items of the test manifest (fixed order, not selected by outcome): base SD 1.5 and SD 1.5 + LoRA
generate from the item's original prompt with the **same seed (1000 + index), 30 steps, CFG 7.5, 512×512**. CLIP
ViT-L/14, DINOv2, SSIM and LPIPS are computed against the DiffusionDB reference image. Results are paired per item:
how often the LoRA image is closer / further / tied, and the mean difference. Images blacked out by the safety
checker are excluded from scoring and counted.

**Interpretation limit:** DiffusionDB references are themselves SD 1.x outputs. An improvement here can mean the
adapter imitates that distribution (sampler, CFG and style habits of 2022 Discord users) rather than that it renders
prompts more faithfully. Use the LoRA selector on the Image Generation page to test the adapter on real reference
photographs with the main A/D/B protocol; the comparison table pairs base and LoRA runs automatically.
